# 07 — MCP Service Endpoint (Model Context Protocol)

**English** | [简体中文](07-mcp.zh-CN.md)

Expose onvif-proxy's management capabilities (device CRUD, RTSP probing,
snapshots, ONVIF self-test, etc.) as MCP (Model Context Protocol) tools to AI
clients (Claude Code / Claude Desktop, etc.), so they can manage this proxy
directly — e.g. "add this RTSP stream as a virtual camera and run a
self-test on it."

- Implementation: the **official Go SDK** `github.com/modelcontextprotocol/go-sdk`
  (currently pinned to **v1.7.0**, co-maintained with Google). This is the
  **sole exception** to the project's "third-party dependencies limited to
  yaml.v3" constraint, on the grounds that the MCP protocol surface
  (lifecycle/session/SSE/multi-version negotiation) is actively maintained
  long-term by the official library, so reimplementing it ourselves has low
  payoff; this exception has been synced into CLAUDE.md and docs/01/06.
- Dependency accounting: `go.mod` has exactly two **direct** requirements —
  `gopkg.in/yaml.v3` and `github.com/modelcontextprotocol/go-sdk`. Every
  other line in `go.mod`/`go.sum` (`golang.org/x/sync`, `golang.org/x/time`,
  `golang.org/x/oauth2`, `golang.org/x/sys`,
  `github.com/google/jsonschema-go`, `github.com/segmentio/asm`,
  `github.com/segmentio/encoding`, `github.com/yosida95/uritemplate/v3`) is
  marked `// indirect` — these are go-sdk's own transitive dependencies,
  pulled in automatically by the go-sdk v1.7.0 upgrade, not dependencies
  this project added on its own. **This does not violate CLAUDE.md's
  "third-party dependencies limited to yaml.v3 and go-sdk" constraint**
  (CLAUDE.md line 24); a longer `go.sum` from a go-sdk bump is expected and
  is not evidence the constraint was broken.
- Transport: Streamable HTTP, a single `/mcp` endpoint, mounted on the
  existing Web UI mux (same port as the REST API), in **stateless mode**
  (`Stateless: true`, no `Mcp-Session-Id` issued). Protocol version
  negotiation and 405/session/SSE details are all handled by the SDK. Request
  bodies are capped at 1 MiB.
- Auth: reuses `withAuth` — when `web.username` is configured, site-wide
  Basic auth applies and `/mcp` is automatically covered as well.
- Go version: the SDK requires Go ≥ 1.25; `go.mod` and the Dockerfile build
  image were bumped in tandem (`golang:1.26.5-alpine`, see docs/05).

Client setup example:

```bash
claude mcp add --transport http onvif-proxy http://<host>:8080/mcp
# When web basic auth is enabled:
claude mcp add --transport http onvif-proxy http://<host>:8080/mcp \
  --header "Authorization: Basic $(printf '%s:%s' user pass | base64)"
```

## 1. Capability declaration

The `initialize` response is generated by the SDK; `serverInfo` is
`{name: "onvif-proxy", version: <Status().Version>}`; only the tools
capability is registered (no resources/prompts). `ServerOptions.Instructions`
is set to:

> onvif-proxy management server: wrap RTSP streams as virtual ONVIF cameras.
> Use list_devices/get_status to inspect, probe_rtsp/get_stream_info before
> adding a device, add_device/update_device/delete_device to manage,
> run_onvif_selftest to verify.

## 2. Tool set

12 tools, all registered on the same `mcp.Server`. JSON results are carried
in text blocks (as a serialized JSON string); snapshots are carried in image
blocks. Input structs are described with `jsonschema` tags, and the schema
is auto-generated by the SDK.

| Tool | Parameters | Result | Corresponding capability | Annotations |
|---|---|---|---|---|
| `get_status` | none | Status JSON (version/advertise_ip/uptime_seconds/ffmpeg) | `Backend.Status` | readOnly |
| `list_devices` | none | array of deviceView JSON (isomorphic to `GET /api/devices`) | `Backend.Devices` | readOnly |
| `get_config` | none | raw config.yaml text | `Backend.ConfigYAML` | readOnly |
| `apply_config` | `yaml` string required; `dry_run` bool default false | success: `"applied"` / `"valid"`; validation failure: isError + raw error text | `Backend.ApplyConfig` | idempotent |
| `add_device` | `device` object required (same structure as the `POST /api/devices` body, see docs/04) | success: `"applied"`; validation failure: isError | reuses `buildDevice` + `ApplyConfig` | *(none — not idempotent)* |
| `update_device` | `uuid` string required; `device` object required | same as above; nonexistent uuid: isError | reuses edit logic (preserves uuid/mac/serial/info; empty auth password retains it; RTSP userinfo omitted for the same stream name retains it) | idempotent |
| `delete_device` | `uuid` string required | same as above | reuses delete logic | destructive, idempotent |
| `probe_rtsp` | `url` string required, must be a well-formed `rtsp://` URL (rejected otherwise, see below) | rtsp.Result JSON | `rtsp.Probe` | readOnly, openWorld |
| `get_stream_info` | `url` string required, must be a well-formed `rtsp://` URL (rejected otherwise, see below) | ffprobe stream-info JSON; missing ffprobe: isError | same as `POST /api/test/streaminfo` | readOnly, openWorld |
| `take_snapshot` | `uuid` string required; `stream` string optional | image block (base64 JPEG); failure/no ffmpeg: isError | `Backend.Snapshot` | readOnly, openWorld |
| `run_onvif_selftest` | `uuid` string required | `[]onvifCheck` JSON (method/http_status/soap_fault/pass) | `runONVIFSelfTest` | readOnly |
| `get_discovery_log` | none | WS-Discovery log JSON | `Backend.DiscoveryLog` | readOnly |

`probe_rtsp` and `get_stream_info` both run their argument through
`validateRTSPURL` (mcp.go:211/223) before doing anything else: any URL that
does not parse as `rtsp://<host>...` (wrong scheme or missing host) is
rejected as a business error (isError), so neither tool can be turned into a
generic port scanner over the URL parameter.

Error semantics:

- **Invalid parameters / unknown tool** → SDK-level protocol error (the
  client receives a JSON-RPC error).
- **Business failure** (probe failure, config validation failure, missing
  ffmpeg, nonexistent uuid, invalid `rtsp://` URL, etc.) → tool result
  `isError: true`, with the raw error text as content. In go-sdk, a handler
  returning a non-nil error is mapped directly to an isError result, and
  this mechanism is used as-is.

### 2.1 Tool annotations

Every tool above carries an explicit `ToolAnnotations` value (`mcp.go`, the
`anno*` vars right after `mcpInstructions`). This matters because the MCP
spec's *unstated* defaults are the worst case for a client UI:
`readOnlyHint` defaults to `false` and `destructiveHint` defaults to `true`
— so a tool left unannotated is treated by clients as potentially
destructive, including pure reads. Annotating all 12 tools avoids that
false-positive noise:

- **Read-only** (`readOnlyHint: true`): `get_status`, `list_devices`,
  `get_config`, `get_discovery_log` — these only read local proxy state.
- **Read-only, open-world** (`readOnlyHint: true, openWorldHint: true`):
  `probe_rtsp`, `get_stream_info`, `take_snapshot` — still reads, but the
  read reaches an external entity (an RTSP camera at a caller-supplied or
  configured URL) rather than just local state.
- **Read-only, explicitly closed-world** (`readOnlyHint: true,
  openWorldHint: false`): `run_onvif_selftest` — it calls the proxy's own
  ONVIF SOAP endpoints on `127.0.0.1` (see `onvif_selftest.go`), not a
  foreign entity, so `openWorldHint` is pinned to `false` rather than left
  at its `true` default.
- **Mutating, non-destructive** (`readOnlyHint: false, destructiveHint:
  false`): `add_device`, `update_device`, `apply_config`. Of these,
  `update_device` and `apply_config` are also `idempotentHint: true`
  (replacing by uuid / applying a full config converge to the same state on
  repeat); `add_device` is **not** idempotent — each call appends another
  device that gets a freshly generated uuid/mac/serial on reload, so
  calling it twice with identical arguments produces two devices, not one.
- **Destructive** (`readOnlyHint: false, destructiveHint: true`):
  `delete_device`. Still `idempotentHint: true`: a second delete of an
  already-removed uuid converges to the same end state (device absent),
  even though that second call itself reports a business error.

**Warning: annotations are UI hints, not a security boundary.** The MCP
spec is explicit that clients must never make tool-use *decisions* based on
`ToolAnnotations` from an untrusted server, because a malicious server can
simply lie about them. Adding these annotations changes nothing about the
actual safety checks in `mcp.go` — `validateRTSPURL` and `withOriginCheck`
still run exactly as before, on every call, regardless of what a tool's
annotations say.

## 3. Implementation contract (internal/web)

New files `mcp.go` + `mcp_test.go`; two small refactors in `devices.go`;
REST behavior unchanged.

**`mcp.go`**:

- `func (s *Server) mcpHandler() http.Handler`: builds an `mcp.Server`
  (`mcp.NewServer(&mcp.Implementation{...}, &mcp.ServerOptions{Instructions: ...})`),
  registers all tools from §2 via `mcp.AddTool`, and returns
  `mcp.NewStreamableHTTPHandler(func(*http.Request) *mcp.Server { ... }, &mcp.StreamableHTTPOptions{Stateless: true})`.
- Uniform tool handler shape: input is a struct with `json`/`jsonschema`
  tags; text results are wrapped with the small helper
  `mcpJSON(v any) *mcp.CallToolResult` (strings passed through as-is,
  everything else via `json.Marshal`).
- Every per-device tool (take_snapshot / run_onvif_selftest / update /
  delete) first calls `s.findDevice(uuid)`, returning an error ("no
  configured device with that uuid") if it doesn't exist.
- `probe_rtsp` and `get_stream_info` first call `validateRTSPURL(in.URL)`
  (mcp.go:211/223), rejecting anything that isn't a well-formed `rtsp://`
  URL before any network I/O happens — see §2.1 for why this stays in place
  regardless of a tool's annotations.
- Every `mcp.Tool{}` registered in `getServer` carries an `Annotations`
  field pointing at one of the shared `anno*` vars declared next to
  `mcpInstructions` (`annoReadOnly`, `annoReadOnlyOpenWorld`,
  `annoSelfTest`, `annoWrite`, `annoWriteIdempotent`, `annoDestructive`) —
  see §2.1 for the classification and rationale.
- **The API is authoritative as output by
  `go doc github.com/modelcontextprotocol/go-sdk/mcp <Symbol>`** (AddTool's
  generic signature, CallToolResult/Content fields, StreamableHTTPOptions)
  — do not write it from memory.
- If the SDK does not build in Origin validation (to prevent DNS rebinding,
  a MUST item in the MCP spec), wrap it at the mount point: when the
  `Origin` header is present and its hostname is neither loopback
  (localhost/127.0.0.1/::1) nor equal to the request `Host`'s hostname,
  respond 403; requests without an `Origin` header pass through.

**`web.go` registration** (in `New`): `mux.Handle("/mcp", s.mcpHandler())`
(no method restriction; GET/DELETE semantics are handled by the SDK).

**`devices.go` refactor**:

- Extract `func (s *Server) deviceViews() []deviceView`, shared by
  `handleDevices` and `list_devices`.
- Extract `func (s *Server) applyParsedConfig(cfg *config.Config) error`
  (marshal + `Backend.ApplyConfig`); the original `applyConfig(w, cfg)` is
  changed to call it; MCP's add/update/delete_device also call it.

Concurrency safety: all config changes go through `Backend.ApplyConfig`
(the manager inside main holds a lock); MCP introduces no new write path.

**`mcp_test.go`** coverage (via `httptest` + the SDK client
`mcp.NewClient` + `mcp.StreamableClientTransport`, over real HTTP):

- initialize succeeds, serverInfo.name = "onvif-proxy";
- tools/list returns exactly 12 tools, all names present;
- `list_devices` / `get_status` return results consistent with the fake
  Backend;
- `apply_config` dry_run validation failure → isError;
- `delete_device` with an unknown uuid → isError;
- calling an unknown tool → error;
- a bare `GET /mcp` (no session) does not panic, returns 4xx;
- a POST with a malicious `Origin` → 403 (if the wrapper layer is
  implemented);
- `take_snapshot` returns an image block whose bytes equal the JPEG the fake
  backend produced (`TestMCPTakeSnapshot`);
- tools/list carries the §2.1 annotation hints — e.g. `get_status` is
  `readOnlyHint: true` with no `openWorldHint`, `probe_rtsp` additionally
  sets `openWorldHint: true`, `delete_device` is the only
  `destructiveHint: true` tool, and `add_device` is the only mutating tool
  that is not idempotent (`TestMCPToolAnnotations`).

## 4. Acceptance

1. `go build ./... && go vet ./... && go test ./...` all green; `go.mod`
   gains only the go-sdk and its transitive dependencies.
2. After starting the service locally, connect with a real client:
   `claude mcp add --transport http onvif-proxy http://127.0.0.1:8080/mcp`,
   and confirm initialize completes, the 12 tools are listed, and
   `get_status` and `list_devices` can be called successfully.
3. The Web UI's existing REST API and page behavior are unchanged
   (regression: built-in ONVIF self-test all green).
